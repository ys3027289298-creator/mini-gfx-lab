# mini-navgrid · 寻路套件

四种寻路算法挂在同一接口 `pf_solve()` 下，按地图特征自动选路，并在三类地图上交叉验证、
跑耗时与扩展数表格。

| 算法 | `PfAlgo` | 实现 | 适用 |
|---|---|---|---|
| A* | `PF_ASTAR` | 8 方向、禁止切角、octile 启发 | 走廊/迷宫，少量开阔区 |
| 任意角度 | `PF_ANYANGLE` | Theta*：视线可达时改挂祖父节点 | 开阔、柱状障碍，要更短更少拐点 |
| 增量重规划 | `PF_INCREMENTAL` | LPA*：地图编辑后只在脏区重算 | 门开关、可破坏场景 |
| 分层 | `PF_HIERARCHICAL` | HPA*：8×8 簇抽象图 + 层内 Dijkstra 建边 | 大图、多房间，跨多次查询 |

```bash
make test    # 自检：几何、四算法、跨算法交叉验证、增量重规划、自动选路
make bench   # 追加耗时/扩展数/路径长度/代价表
```

## 接口

```c
#include "pf.h"

PfGrid g;
pf_grid_load(&g, rows, h);            /* 或 pf_grid_init + pf_grid_set */
PfSolver* s = pf_solver_new(&g);      /* solver 拥有网格副本 */

PfPoint a = {0,0}, b = {8,4};
PfPoint buf[1024];
PfPath p;  pf_path_init(&p, buf, 1024);
int rc = pf_solve(s, a, b, PF_AUTO, &p);   /* rc: PF_OK / PF_ENOPATH / ... */
pf_path_valid(&g, &p, p.algo == PF_ANYANGLE);

pf_solver_set_blocked(s, x, y, 1);    /* 地图编辑会自动让相关缓存失效 */
pf_solver_set_changes_expected(s, 1); /* 提示 PF_AUTO 选增量算法 */
pf_solver_free(s);
```

`PfPath.cost` 是路径真实折线长度，`PfPath.expansions` 是本次查询弹出的节点数
（HPA* 含层内搜索、LPA* 含重算节点），`PfPath.algo` 是实际执行的算法
（`PF_AUTO` 时由 `pf_select_algo()` 决定）。

## 自动选路 `pf_select_algo()`

先算地图画像（阻挡率、走廊率、岔口率、面积），然后：

1. `changes_expected` → **增量**（只有编辑会弄脏已有计划）
2. 走廊率 ≥ 0.55 → **A***（单格走廊里任意角度没有收益）
3. 面积 ≥ 96×96 且阻挡率 ≥ 0.05 → **分层**（簇抽象摊薄开销）
4. 其余 → **任意角度**

近空的大图仍走任意角度，因为分层的建图开销换不来收益。

## 交叉验证

`make test` 在开阔、迷宫、多房间三类地图上对每个算法逐项断言：

- 路径在其自身移动规则下合法（相邻步或视线可达）、端点正确、`cost` 与折线长度一致；
- **A* 与 LPA* 逐点一致**：两者都用同一套 8 连通最优路径重建
  （`pf__descend_optimal()`，固定方向序打破等价代价），所以是点序列相等而非仅代价相等；
- **任意角度 ≤ A***：移动规则更宽，只可能更短；
- **分层不优于 A*，且不超过 A* 的 5%**：抽象图只可能绕远，所以是上界；
  三类地图实测差距 0% / 0% / 0.43%，断言留 5% 余量（详见文末"已知取舍"）。

规模更大的随机压力测试（随机障碍、随机编辑、相邻起终点、无路场景）不在 `make test`
里，但同一组断言也成立。

## 重规划（编辑后重算，128×128，`make bench` 第二张表）

沿当前最优路径开一扇门（旁边没墙时就堵一格，堵断地图的样本跳过），比较从头 A* 与
增量重算：

| 地图 | A* | 增量 | A* 扩展 | 增量扩展 |
|---|---:|---:|---:|---:|
| 开阔 | 0.088 | 0.075 | 648 | 154 |
| 迷宫 | 0.197 | 0.364 | 3559 | 3096 |
| 多房间 | 0.565 | 0.583 | 3614 | 1438 |

增量在开阔图省时间；三类图都省扩展数（1.2×–4.2×）。迷宫/多房间上不省时间，因为
编辑附近的传播仍然稠密，单次查询的簿记成本比 A* 的紧凑循环高。这不是退化：
LPA* 的价值在扩展数与"编辑越多越划算"的累计曲线上。

## 分层建图的开销与回本点

HPA* 的抽象图按每簇"每个边界节点一次 Dijkstra（只走到其余边界节点就停）"构建，
成本与边界节点数成正比。128×128 多房间图有 4916 个边界节点、约 9.9 万条抽象边，
建图约 13 ms、热查询 0.25 ms。规模越大回本越快：

| 边长 | A* | 分层冷启动 | 分层热查询 | 回本查询数 |
|---:|---:|---:|---:|---:|
| 64 | 0.22 | 3.9 | 0.07 | ~24 |
| 128 | 0.79 | 15.4 | 0.37 | ~35 |
| 192 | 1.84 | 38.0 | 0.89 | ~38 |
| 256 | 3.74 | 67.5 | 1.92 | ~35 |

所以分层适合"同一张图反复查询"的场景；单次查询用自动选路会选到 A* 或任意角度。
地图编辑会让抽象图失效并触发重建，这也是 `pf_select_algo()` 在 `changes_expected`
时优先选增量的原因。

## 已知取舍

- **任意角度用格子中心点路径**：Theta* 的拐点在格子中心，不做"漏斗"贴墙处理，
  所以路径合法但不贴边；代价与折线长度严格一致，便于和其他算法比。
- **分层不保证最优**：抽象图限定了跨簇的穿越点，HPA* 没有"不超过 A* 某个固定倍数"
  的定理，只有经验上的接近。`make test` 在固定三类地图上按 5% 断言（实测 0% / 0% / 0.43%）；
  另有 589 张随机障碍图（24–133 边长、2%–36% 阻挡率、随机起终点）实测：
  平均 0.005%、最差 2.27%、无一超过 5%。所以 5% 是经验界不是定理，
  要当硬约束用请先在自己的地图上跑一遍。
- **增量算法依赖编辑半径 5×5**：禁止切角意味着编辑一格会改变斜向步的合法性，
  所以刷新半径取 2 而不是 1；漏掉外圈会让路径偶发丢失。
- **地图上限 256×256**：与其它模块一致的固定上限，超出由 `pf_grid_init()` 拒绝。
